# 路由误判事故记录：工具调用打到别的游戏（2026-11-15 ~ 11-16）

本文是一次线上事故的记录 + 根因 + 建议，配套两套回归集：
`tests/test_routing_regression.py`（代码层）与
`scripts/eval/agent_behavior.py` + `scripts/eval/behavior_cases.jsonl`（模型层）。
评测体系本身见 `docs/EVAL_SYSTEM.md`。

## 1. 现象

用户提问 BG3 内容，落库的 `game` 字段与工具调用实际使用的 `game` 参数是别的游戏，
检索走了错的库：

| 时间（2026） | 提问 | 落库 game | 实际正确游戏 |
|---|---|---|---|
| 11-15 23:16 | 水电工怎么玩 | `oni` | `baldurs_gate3`（潮湿+闪电流派） |
| 11-15 23:46 | 护符里的幽灵那个任务的 | `hollow_knight` | `baldurs_gate3`（感知护符任务） |
| 11-15 23:47 | 帮助他到最后，他问我要不要继承莎尔的诅咒，学会狂笑术，但是有代价 | `hollow_knight` | `baldurs_gate3` |
| 11-16 00:14 | 明萨拉用压迫灵魂之剑还是静止者？我选的是单手武器+盾牌的职业 | `hollow_knight` | `baldurs_gate3` |

证据链（都可复现）：

- `data/turns/2026-11-15.jsonl` / `2026-11-16.jsonl` 四条记录的 `game` 字段。
- `api_server.log:202`：`📥 加载向量库：games/hollow_knight/vectorstore → 1960 个向量`
  正是 23:45:57 那轮（护符里的幽灵）触发的——该轮之前所有轮次都只用 BG3 库，
  HK 库是本轮首次加载，说明工具确实被调到了 `game="hollow_knight"`。
- 23:45 那轮回答自述「以下机制来自博德之门3知识库」，23:46 那轮自述
  「我这次调用知识库和结构化数据库时，返回的全是《空洞骑士》的资料」——
  模型侧确认了工具返回的是错游戏的数据。

## 2. 影响面（比"答不上来"更严重的两点）

1. **伪造引用**。23:47 那轮回答写：「（来源：知识库「帮助护符中的灵魂（Help the Spirit
   of the Amulet）」/「Monk's Manifestation」/「感知护符（Sentient Amulet）」条目；
   结构化数据库 items 表未收录此护符）」。HK 库里不存在这三条，来源行是编的。
   用户无法分辨「真检索到」和「模型自己编的来源」，这比检索落空危害大得多。
2. **绕过剧透边界**。23:46 那轮走了「模型常识」路径，直接给了「位于第三章下城区」，
   而用户当时在第二章。工具路径有 act 过滤与提示词上界，兜底路径没有任何约束。
   按 `docs/SPOILER_SEVERITY.md` 的分级，「下城区」这类地名属 **L1 轻度**
   （越界但几乎不损体验）——这条记录的价值在暴露「兜底路径无进度约束」的机制缺口，
   不在内容杀伤力；同一轮里真正重的是上面的伪造来源。

## 3. 根因

### 3.1 部署漂移（先排除）

出事的 API 进程启动时间 `2026-11-15 13:24:11`，而 `c9f3f90`
（fix(routing): 会话上下文不再被泛游戏用语打断，切换权交给用户）提交于 13:58。
**线上跑的是 13:58 之前的代码**，`oni` 的「电/热」单字信号当时还在。
`c9f3f90` 之后「水电工怎么玩」已不再误判 oni——用 HEAD 代码离线复现可确认，
这条属于「已修但没上线」，不是当前代码的缺陷。

### 3.2 单信号即切换，没有切换门槛

`graph.detect_game_node` 的决策顺序是：`confidence >= 0.4` 就认「点名了已知游戏」，
即使本轮已经有一个 `last_game` 且 `last_game_confirmed` 也同样照切（只多打一句
"用户切换了话题" 的提示）。而 `detect_game` 里任何**单个**信号词就给出
`confidence = 1.0`（唯一命中时 score/total = 1.0）。

于是「护符」「灵魂」这类**跨游戏通用词**成了硬切换开关：

- 「护符里的幽灵那个任务的」→ HK signals 命中「护符」→ conf 1.0 → 从 BG3 切到 HK；
- 「明萨拉用压迫灵魂之剑还是静止者」→ 命中「灵魂」→ 同上。

`hollow_knight.signals` 里同时存在 `"灵魂"` 和 `"护符"`，这两个词在 BG3、泰拉瑞亚、
几乎所有含装备系统的游戏里都会出现；`baldurs_gate3.signals` 里的 `"法术"` 同理。

### 3.3 错误会被历史粘住（机制正确，起点错误）

切换后 `last_game_confirmed = True`，后续每轮「无强信号就沿用 last_game」
（3.2 之前那次修复引入的粘性）会把错误的 HK 一路沿用：
23:47 的追问、次日 00:14 的新问题都被带偏，直到用户手打「BG3」才纠正。
粘性本身是对的，问题在于它粘的是被通用词带偏的起点，且纠正成本落在用户身上。

### 3.4 兜底路径缺两道约束

检索落空 / 游戏判错后走 `fallback`（`_FALLBACKPT` + 模型常识）时：

- 没有剧透约束（3.2 的第二章 → 第三章泄露）；
- 没有引用校验，模型可以把「来源：知识库「X」」写成不存在的条目。

## 4. 建议（按性价比排序，均不碰检索与提示词分层）

| 优先级 | 改动 | 位置 | 预估 |
|---|---|---|---|
| P0 | **切换门槛**：已有 `last_game` 且 confirmed 时，单信号词不足以切换，需「≥2 个信号词」或「命中 exact_patterns / 显式游戏名」 | `graph.detect_game_node` | ~15 行 |
| P0 | **通用词降权**：`灵魂`、`护符`、`法术` 这类跨游戏词从 signals 移到弱信号表，只在"无历史/无其他证据"时用于新会话定向；切走已有会话必须靠专有词 | `game_registry` + `detect_game` | 纯配置 |
| P1 | **引用校验**：答案里的「来源：知识库「X」」，X 必须出现在本轮工具返回文本中，否则剥掉该引用（只检测不改写先跑几天，看误伤率） | 答案后处理 / 复用 L3 审计通道 | ~40 行 |
| P1 | **兜底路径补约束**：`_FALLBACKPT` 增加"不越用户进度、不给后期地点名、不编来源" | `graph._FALLBACKPT` | 纯文案 |
| P2 | **部署校验**：`api.sh` 启动后比对 `/api/status` 的 version 与 `git describe`，不一致提示重启；进程启动时间早于 HEAD 提交时间也报警 | `scripts/deploy/api.sh` | ~10 行 |
| P2 | **兜底可观测**：`turn_record` 增 `game_source`（`history`/`signal`/`explicit`）与 `tool_games`，误判不用再靠 vectorstore 加载行反推 | `api_server.turn_record` | ~10 行 |

不建议的方向：直接删掉 `灵魂`/`护符` 让 HK 更"干净"——新会话里「这个护符怎么拿」
会失去唯一定向线索；弱信号表 + 门槛比删除更稳。

## 5. 回归集挂载点

代码层（`tests/test_routing_regression.py`）：

- 本表四条线上轮次 → 用例 `online-2026-11-15#2316/#2346/#2347`、`online-2026-11-16#0014`；
- 单通用词不切换 → `test_generic_signal_alone_does_not_switch`（P0 未落地前 xfail strict）；
- 显式游戏名仍要能切 → `test_explicit_game_name_switches`（防止 P0 把正当切换一起掐掉）；
- 会话中段不弹菜单 → `test_no_menu_mid_session`。

模型层（`scripts/eval/agent_behavior.py`）：

- `bg3-amulet-chain`、`bg3-minthara-weapons`、`bg3-wet-lightning` 复现误判场景，
  断言工具 `game` 参数与落库游戏一致、答案无伪造来源、无不越界内容；
- `hk-charm-slot`、`bg3-to-hk-switch`、`bg3-to-oni-switch` 是对照组，
  防止修复把「护符」类正常定向和跨游戏切换一起改坏。
