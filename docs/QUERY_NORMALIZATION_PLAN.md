# 输入理解与纠错层（query normalization）设计

状态：方案待评审，未实现
日期：2026-11-17
作者：服务器端（数据分析 + 设计），实现归 Mac 端
关联：`src/rag_agent/glossary.py`（已有，未接线）、`docs/P0_ROUTING_GATE_PLAN.md`

---

## 1. 为什么现在提这个

11-16 一天 63 轮真实对话里，用户输入的专名经常和库里的名字对不上。这不是用户的问题，是产品该在入口处处理掉的事。

从 turns 数据里抽出来的实际样本：

| 用户写的 | 库里的规范名 | 偏差类型 |
|---|---|---|
| 明莎拉 / 明萨拉 | 明萨拉（Minthara） | 同音字，两种写法都出现过 |
| 阿斯带轮 / 阿斯戴伦 | 阿斯代伦（Astarion） | 同音字，三种写法 |
| 素能学派 | 塑能学派（Evocation） | 同音字 |
| 压迫灵魂之剑 | 受压迫灵魂之刃（Blade of Oppressed Souls） | 记错 + 同音 |
| 翩越清风 / 守护火花壁垒 / 静止者 / 卓尔镶钉皮甲 / 半影皮甲 | 未收录或英文未对译 | 术语表覆盖不到 |

现在遇到这些，系统只有两条路：检索零命中，或者靠 LLM 凭常识硬猜再让用户自己发现不对。前者表现为「两个来源都查不到」（27/141 轮出现），后者更糟，答案看着像真的。

用户问的是：能不能在最前面做一个「这是不是某个专名、有没有口误」的判断，置信度高就直接按正确理解往下走，不追问。

能。而且比我们现在的做法省。

---

## 2. 设计目标与硬约束

目标：

1. 把「用户说的词」对齐到「库里的实体」，让检索、路由、术语扩展都拿到干净输入。
2. 置信度高时静默改写，不打断对话。用户明确不喜欢被追问。
3. 任何时候都不能因为改写把问题导向错误答案。宁可漏改，不可错改。

硬约束：

- 纯算法，不调 LLM 做纠错。一次纠错调一次模型，成本比省下来的检索还高，而且结果不可复现。
- 不改写非专有名词。「这个武器怎么样」里的「武器」不能被改成任何东西。
- 改写必须可观测：每一次改写都写进 turn 记录，能回放、能审计、能一键关掉。
- 不做主动追问，任何置信度下都不弹「你是不是想问 XX」。

## 3. 分三层，先做前两层

### L1 别名/变体归一（确定性的，风险最低）

词表来源：

- `games/baldurs_gate3/data/baldurs_gate3_glossary.jsonl`（4238 条，字段 name_en / name_zh / kind / conf / variants / wiki_freq）
- 各游戏结构化表里的实体名：weapons 429、armor 506、items 466、spells 593、characters 2038、locations 249、quests 152、books 735（部分与术语表重叠）
- `game_registry.py` 的 GAME_SIGNALS（游戏专名信号词）

把这几个来源合并成一张内存索引：

```
alias_index[归一化后的串] = [Entity(zh, en, kind, conf, wiki_freq, game), ...]
```

归一化规则：去空格、去标点、繁简统一（可选）、英文小写。

变体现在基本是空的，需要补：中文译名常有两种写法（音译选字不同），英文有所有格、缩写、带前缀的变体（`Astarion's` / `The `）。补法不是靠模型，是从 wiki 正文里统计同一个 en 名的中文共现写法和引号内变体，自动生成候选、人工抽检 100 条。

### L2 同音/形近模糊匹配（有余量时做）

只对「疑似专名片段」做，不扫全句。片段判定：连续中文 2 到 8 字、不是常见词表里的词、不是纯数字。

候选缩小用桶：首字 + 长度。然后按以下顺序打分：

- 拼音完全相同（全拼比较，忽略声调）→ 0.9 起
- 编辑距离 1 且长度相同 → 0.8 起
- 编辑距离 2 且长度 ≥ 5 → 0.7 起
- 再叠加实体权重：`+0.1` 如果 wiki_freq 在同类里排前 20%，`-0.1` 如果 kind 是路人 NPC（conf < 0.5）

拼音库需要 pypinyin，纯本地计算、可预生成映射表（几千条名字，构建时一次性写入 JSON），运行时不做拼音计算。

### L3 中文到英文的检索扩展（已有）

`glossary.py` 现在做的事。顺序上它必须在 L1/L2 之后：先纠错，再扩展。

## 4. 门控：三道闸，任何一道不过就不改

第一道，分数闸：

| 分数 | 行为 |
|---|---|
| ≥ 0.85 且候选唯一 | 静默改写 |
| 0.70 到 0.85 且候选唯一 | 改写，回答开头一句「我按 XX 理解」 |
| < 0.70 | 不改 |
| 前两名分数差 < 0.05 | 不改（不猜） |

第二道，有效性闸：改写前后各跑一次 `detect_game_detail` 和一次轻量检索探测（只查向量库 top1 的相似度，不调 LLM）。只有「改写后确实命中实体或游戏锚点」时才采纳，否则丢弃。这条防的是把「翩越清风」改成某个八竿子打不着的装备名。

第三道，白名单闸：以下词永不替换——通用词（武器、护甲、任务、技能、法术、职业、Boss、地图）、游戏名、数字、单字。

## 5. 与路由的关系

归一化发生在 `detect_game` 之前，改完的名字就是路由的输入。

这解决了一个现存缺口：短追问没有锚点。实测几条：

```
detect_game_detail("素能学派是什么")        -> (None, 0.0, False)
detect_game_detail("翩越清风呢")            -> (None, 0.0, False)
detect_game_detail("守护火花壁垒呢")        -> (None, 0.0, False)
```

这些如果出现在新会话第一句，会直接落菜单。归一化到「塑能学派」后，至少能命中 spell/class 相关实体，路由有据可依。

反过来，如果改写引入了一个跨游戏的词，会把路由带偏。所以第二道闸里必须包含路由复测。

## 6. 落地清单

新增 `src/rag_agent/normalizer.py`：

```python
build_alias_index(games_dir) -> dict      # 离线构建，产物 JSON 落 games/<game>/data/alias_index.json
normalize_query(question, game=None) -> NormalizeResult
#   NormalizeResult: text, rewrites=[{src, dst, score, kind}], changed: bool
```

接入点：`graph.py` 的入口（`_build_initial_state` 之后、检测游戏之前），默认开关 `normalize.enabled=false`，先跑影子模式。

观测：turn 记录新增 `norm_rewrites` 字段（最多 3 条），不改变现有字段。

不做的事写在这里，防止后面加戏：不调 LLM、不追问、不改写通用词、不做跨游戏猜测（会话里锁定 BG3 时不去匹配 HK 的词）。

## 7. 怎么证明它有用

离线回放，不碰线上：

1. 拿 `data/turns/*.jsonl` 的 141 条真实问题跑 `normalize_query`，统计会被改写的条数。预期在 5% 到 15% 之间，超过 20% 说明门控太松。
2. 人工抽检全部改写样本，正确率目标 ≥ 95%。
3. 对比改写前后的 `detect_game_detail` 命中数，以及在向量库上的 top1 相似度均值。目标：命中数增加，且没有一条改后相似度下降。
4. 挑 10 条真实问题做端到端 A/B（同一会话、同一模型），人工判断答案是否更好。这一步由用户在 Mac 上跑。

验收口径沿用项目惯例：新增用例先失败、接入后转绿。`tests/test_normalizer.py` 全部纯函数，不调模型、不查库。

---

## 8. 什么时候做

排在 history 裁剪之后。理由是纠错层的收益要在「检索命中率」上体现，而现在的上下文膨胀正在同时污染输入和输出，先止血再优化检索。

如果只做一件事，先做 L1 别名归一 + glossary 接线，这两个加起来能覆盖大半错字场景，工作量不到一周。
