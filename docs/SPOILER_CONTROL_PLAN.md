# 防剧透设计问题与改造方案

> 来源：服务器端（线上数据）日志分析，2026-11-12 提出，交 Mac 侧主导实现。
> 分工依据 AGENTS.md「运行环境分工」：提示词/数据层属核心 RAG（Mac 主导），
> 观测与回归样本属用户数据沉淀（服务器侧负责）。

## 一、线上证据

11-12 上午，真实用户在浏览器里连续三轮（来自 `api_server.log` 的 `turn` 记录，
无答案留存，以下为 question + 指标）：

| 时间 | 提问 | 工具调用 | tokens_in |
|---|---|---|---|
| 11:21:20 | 可能是我记错了名字，应该就是暗夜之矛吧 | 2 | 7,494 |
| 11:22:12 | 光旅馆还有一个探寻塞伦捏的秘密的任务 | 5 | 27,224 |
| 11:23:57 | 这有一个问题，你不要告诉我我卡住的地方后面太多的内容啊，石匠工会什么的？我卡在旅店你就讲旅店对不对？ | 1 | 9,556 |

第二轮是越界点：用户当时在「最后之光旅店」（Act 2 中段），提问关于旅店附近的
塞伦捏抵抗组织任务；回答把整条任务链的后续区域一起讲了，包括石匠工会
（Mason's Guild，Act 2 后段地点）。第三轮用户明确抗议并要求「我卡在旅店你就讲旅店」。

第二轮 27.2k `tokens_in` 是本次会话最高，说明检索把后续章节的条目一并塞进了上下文——
不只是措辞问题，是检索范围没有边界。

另注：BG3 在接上向量库之前答得含糊反而不越界；库接上、检索变强后，越界成为必然。

## 二、现状机制盘点

1. 剧透规则只存在于通用提示词 `src/rag_agent/game_router.py::build_common_rules()`
   的「## 剧透管理」小节（第 122–129 行），内容为：
   - 默认不主动透露关键剧情
   - 剧情类问题先追问进度（举例只有 VA-11 Hall-A / Cyberpunk 2077 问「第几天/第几章」，
     空洞骑士 / 泰拉瑞亚问「已获得能力 / 已击败 Boss」）
   - 超出进度的内容只做模糊提示
   - 用户要求剧透或声明通关时放开
2. **BG3 没有落在任何一类里**：`src/rag_agent/game_registry.py` 的 BG3 配置（第 295–344 行）
   `extra_prompt` 只写了 5e 术语与结构化表说明，没有一个字涉及剧透或进度。
   实际效果：BG3 既不追问章节，也没有进度上界。
3. 规则只有「先追问」，没有「用户已报进度后以此为止、不再重复问」，
   也没有「用户明确说别剧透时如何记录边界」。
4. 检索层没有任何边界：`tools.search_knowledge_base()` 是纯 top-k=8，
   文档元数据里没有章节/区域字段，检索会跨章返回（实测检索 `Mason's Guild`
   返回的文本自带 `categories: Act_Two_Locations`、`act: 2`，但这只是正文内容，
   拿不到 filter 层）。
5. 进度只活在请求 `history` 里（`multi_agent._game_from_history`），刷新即丢，
   没有服务端 session。
6. 答案不落盘：`turn_record()` 只记 question 与指标，无法事后审计越界内容，
   也无法沉淀剧透回归样本。

## 三、改造方案（分层，按性价比排序）

### P0 提示词层（零数据改动，当天可落地）

- `game_router.build_common_rules()` 重写「剧透管理」：
  - 把「剧情推进型游戏」的判定改为**按游戏标注**，不再靠举例：在
    `game_registry.py` 每个游戏加一个 `spoiler_axis` 字段
    （`act` / `chapter` / `ability` / `none`），BG3 = `act`，
    CP2077、VA-11 Hall-A = `chapter`，空洞骑士、丝之歌、泰拉瑞亚 = `ability`，
    缺氧、MHW = `none`。
  - 规则明确：**用户报过进度后，进度构成硬上界**，后续回答不得越过；
    再次提问时不再重复追问进度；用户若说「别剧透后面」，必须在作答前复述边界
    （「你现在在最后之光旅店，我只讲这一带」）。
  - 明确「超出上界」不得正向描述（不给名字、不给结果），只允许
    「还有后续，等你到那儿再说」这类占位提示。
- `game_registry.py` BG3 `extra_prompt` 补一段：说明本作三幕结构、
  常见进度锚点（第一章地表/幽暗地域 → 第二章最后之光旅店/月出之塔 → 第三章下城区），
  并说明结构化数据里 locations / quests 带 act 列可供判断。

### P1 数据层（给检索装边界，需重建 BG3 向量库）

- 结构化侧已具备条件（无需新采集）：
  `games/baldurs_gate3/data/baldurs_gate3_data.db` 的
  `locations`（249 行）、`quests`（152 行）都有 `act` 列（取值 1/2/3）。
- 建库时（`scripts/tool/mac_build.py::collect_documents()`）给文档补
  `act` 元数据：
  - 结构化 locations / quests：直接取 `act` 列；
  - wiki 文档：正文/分类里带 `Act_One_*` / `Act_Two_*` / `Act_Three_*`
    的按分类解析（BG3 wiki 的 categories 字段已经落在文本中，
    实测可用）；解析不出的**不写该字段**（视为 unrestricted）。
- `tools.search_knowledge_base()` 增加可选参数 `max_act`：
  带 filter 过滤，**缺 `act` 字段的文档默认保留**（否则纯设定类词条会被误杀）。
  注意 FAISS 的 dict filter 只做等值，区间判断要用 callable filter，或
  预先把 act 拆成 `acts: ["1","2","3"]` 列表做成员匹配（推荐后者，性能与可读性都更好）。
- 谁来决定 `max_act`：短期由模型在调用时传（提示词要求「已知进度时必须带」），
  中期由服务端 session 注入（见 P2）。

### P2 会话层（中期，需服务端参与）

- 服务端持久化 `progress`（game → act/chapter/ability），随每轮注入，
  取代从 `history` 反推；顺带解决「刷新即失忆」。

### P3 观测层（服务器侧负责）

- `turn_record()` 增加 `answer_head`（答案前 200 字）与 `spoiler_flags`
  （命中的越界区域名/黑名单词），先落 `api_server.log`，随后接 turns 表。
- 建立剧透回归样本：本次「最后之光旅店 + 塞伦捏任务」即第一条，
  断言回答不得出现 `Mason's Guild / 石匠工会 / Grand Mausoleum / 大陵墓 / 月出之塔` 等
  后续区域名（按用户进度锚点设置黑名单）。

## 四、验收标准

1. 以「我卡在最后之光旅店」为前提提问旅店附近任务，回答中不出现石匠工会、
   大陵墓、月出之塔等后续区域名（黑名单比对，P3 提供自动化）。
2. 未报进度时先问进度；报过进度后**不再重复追问**（连续两轮同一问题只问一次）。
3. 用户明说「别剧透」后，回答开头必须出现边界复述。
4. 检索日志中 `max_act` 实际生效：Act 2 进度下不应返回 `act=3` 的 quest/location 文档。
5. 通过重建后的 `mac_prepare_build.sh` 第 5 步自检（走真实
   `tools.search_knowledge_base` 路径）+ `tests/test_mac_build_contract.py`。

## 五、待裁决

1. act 粒度够不够：地点/任务是地理维度，但「影心身世」「皇帝身份」这类是剧情揭秘维度，
   不是 act 能挡的。是否再加一个 `spoiler: core/none` 标签？建议**先不加**，
   先用提示词层兜，避免一次上两个过滤轴。
2. wiki 条目 act 推断不出来的（设定、法术、物品类）默认放行是否可接受？
   建议放行——它们通常不含区域剧情。
3. 越界时的处理风格：占位提示（「等你到那儿再说」）还是直接拒答？建议前者。
