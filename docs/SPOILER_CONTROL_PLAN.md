> 来源：服务器端（线上数据）日志分析，2026-11-12 提出，2026-11-15 补充「用户进度」一节。
> 交 Mac 侧主导实现提示词与数据层；进度推断、L3 审计、观测与回归样本归服务器侧。
> 分工依据 AGENTS.md「运行环境分工」：提示词/数据层属核心 RAG（Mac 主导），
> 观测与回归样本属用户数据沉淀（服务器侧负责）。

## 二、现状机制盘点

1. 剧透规则只存在于通用提示词 `src/rag_agent/game_router.py::build_common_rules()`
   的「## 剧透管理」小节（第 122–129 行），内容为：
   - 默认不主动透露关键剧情
   - 剧情类问题先追问进度（举例只有 VA-11 Hall-A / Cyberpunk 2077 问「第几天/第几章」，
     空洞骑士 / 泰拉瑞亚问「已获得能力 / 已击败 Boss」）
   - 超出进度的内容只做模糊提示
   - 用户要求剧透或声明通关时放开
2. **BG3 没有落在任何一类里**：`src/rag_agent/game_registry.py` 的 BG3 配置（第 295–344 行）
   `extra_prompt` 只写了 5e 术语与结构化表说明，没有一个字涉及剧透或进度。
   实际效果：BG3 既不追问章节，也没有进度上界。
3. 规则只有「先追问」，没有「用户已报进度后以此为止、不再重复问」，
   也没有「用户明确说别剧透时如何记录边界」。
4. 检索层没有任何边界：`tools.search_knowledge_base()` 是纯 top-k=8，
   文档元数据里没有章节/区域字段，检索会跨章返回（实测检索 `Mason's Guild`
   返回的文本自带 `categories: Act_Two_Locations`、`act: 2`，但这只是正文内容，
   拿不到 filter 层）。
5. 进度只活在请求 `history` 里（`multi_agent._game_from_history`），刷新即丢，
   没有服务端 session。
6. 答案不落盘：`turn_record()` 只记 question 与指标，无法事后审计越界内容，
   也无法沉淀剧透回归样本。

## 三、用户进度：怎么来、怎么存、在哪一层生效（2026-11-15 补充）

这一节是整套方案的骨架。前面 P0–P2 说的是「往哪层加约束」，这节说的是
**约束的那个上界从哪儿来**。没有它，分层防御全是空转。

### 3.1 为什么把「进度」当一等公民

提示词层「先追问进度」实测不管用：

- 11-12：用户明说「我卡在旅店你就讲旅店」，上一轮仍讲了石匠工会；
- 11-14 第 2 轮：用户在第 2 章停尸房，答案里出现 `下城区`、`Bhaal`（act 3），
  `spoiler_hits` 捕获到，问句只有 27.5k tokens 级别的上下文，说明检索把第 3 章
  的条目直接塞进了上下文。

只要第 3 章的文档进了上下文，模型看见了就会用 —— 这不是措辞纪律问题。
结论：**进度必须是结构化状态，被检索层消费**，不能只活在模型的一句话里。

### 3.2 进度对象

```python
Progress = {
    "game": "baldurs_gate3",
    "axis": "act",              # act | chapter | day | none
    "level": 2,                 # 数值；未知 = None
    "source": "user",          # user | inferred | question | default
    "evidence": ["月出之塔"],   # 推断依据，便于事后核对
}
```

规则三条：

1. **单调不减**。推断只能上调；下调只认用户明说「我重开了 / 新周目」。
2. **多来源取 max**：`level = max(前端值, 推断值, 提问所指)`。
3. **提问即授权**：问「第三章怎么打」等价于要第三章的信息，`level` 至少抬到 3，
   否则会把自己卡住、答得没法用。

### 3.3 三个来源

| 来源 | 可靠性 | 实现 | 状态 |
|---|---|---|---|
| 前端显式设定 | 最高 | 请求 body 加 `progress: {game, axis, level}`，localStorage 记住，页面一个下拉（未设置 / 第一章 / 第二章 / 第三章）。未设置就不发 | 待前端 |
| 对话推断 | 中 | `rag_agent/progress.py`：用 `SPOILER_TERMS`（带 act 词表）+ 结构化库 `locations`/`quests` 的 `act` 列，扫 history 的 user 消息与本轮问题，取最大 act | 我做 |
| 提问所指 | 高 | 同上，命中当前问题里的 act 词就抬 | 我做 |

推断模块必须是**纯函数**（输入 history + question → Progress），好单测、也好在
`tools.py` 里被检索侧复用。

### 3.4 未知进度怎么办：不问，按「提问所指」作答（方案 C）

三个候选，已定 C：

- A「先问进度再答」——**否决**。11-14 实测被用户直接打「BG3」催；重复追问本身就是
  体验事故，和「不要反复汇报」的偏好相冲。
- B「默认最保守（第一章）」——**否决**。第 2 章的用户会拿到一堆没用的含糊话。
- C「不问，上界 = max(推断值, 提问所指 act)」——采用。具体：
  - 问题指向某幕 → 按那幕作答，后续发展压住；
  - 问题完全不指向某一幕 → 最小剧透作答：只讲怎么去、怎么触发，不展开后续结果；
  - 答案结尾一句边界说明（「我按第二章给你讲的，过了 X 再问我细说」），
    **不重复追问**；
  - 「告诉我进度我能讲得更细」这类话，一个会话最多出现一次。

### 3.5 在哪一层生效（缺一层就漏）

| 层 | 做什么 | 依赖 | 责任 |
|---|---|---|---|
| L1 检索层 | `max_act` 过滤，act > level 的文档不进上下文；缺 `act` 字段放行 | Mac 重建带 act 元数据 | Mac 建库 + 服务器接线 |
| L2 提示词层 | 把进度写成硬上界句（「用户进度=第二章，禁止提及第三章之后的地点/敌人/结局；进度已知，不要再问」） | 无 | Mac 改 `build_common_rules()`；服务器把 progress 注入 state |
| L3 后置审计 | `spoiler_hits` 里 `max(act) > level` → 带严格版提示重写一次；仍越界则换成占位提示「这段涉及你之后的进度，要不要我讲」 | 已有 hits 机制 | 服务器 |

L3 不是替代品：它只能救措辞，救不了「上下文里全是第 3 章资料」这个事实。
L1 落地前，L2+L3 是止损。

### 3.6 份数、存储与观测

- 短期无状态：进度 = 前端字段 + 当轮推断，随 history 走，刷新靠前端 localStorage 兜；
- 中期归服务端：既定计划里 `store.py` 的 `sessions` 表加 `progress` 列，
  服务端成为真理源，顺带解决「刷新即失忆」；
- 观测：`turn` 记录加 `progress_level` / `progress_src`，看两天真实流量就知道
  上界有没有生效、act3 泄漏率降没降。

### 3.7 轴的定义（只做剧情类）

| 游戏 | axis | level 取值 |
|---|---|---|
| 博德之门3 | act | 1 / 2 / 3 |
| 赛博朋克2077 | chapter | 主线阶段 |
| VA-11 Hall-A | day | 天数 |
| 空洞骑士 / 丝之歌 / 泰拉瑞亚 / 缺氧 / MHW | none | 不分级，只保留现有剧透话术 |

非剧情类硬造章节只会变形。它们的剧透风险是「后期 Boss / 结局 / 隐藏区域」，
靠现有「超出进度只做模糊提示」的规则兜。

### 3.8 落地顺序与分工

1. **服务器**：`progress.py`（推断）+ L2 注入 + L3 审计重写 + 观测字段 → 我先做；
2. **服务器**：`query_structured_data` 按 `act` 过滤（quests/locations 已有列，不依赖建库）；
3. **Mac**：P0 提示词层重写（`spoiler_axis` + 按字段生成规则 + BG3 三幕锚点）；
4. **Mac**：重建带 act 元数据 → **服务器**接线 L1 硬过滤；
5. **前端（用户）**：进度下拉；
6. 词表从手工 `SPOILER_TERMS` 改为从结构化数据派生（等 act 元数据齐了再做）。

顺序 1 不依赖任何人，可以先上线止损；2 紧随；3/4 等 Mac；5 有空再加。

### 3.9 本节新增验收

1. 第 2 章会话问「停尸房 / 旅店附近」，答案不出现 `下城区`、`巴尔`、`主脑`、`利文顿`；
2. 同一话题连续追问两轮，**不重复**问进度；
3. 直接问「第三章怎么打」时不问进度、按第三章答（提问即授权）；
4. `turn` 记录里 `progress_level` 与实际对话对得上（可抽样人工核对）；
5. 用户明说「别剧透」时，同一会话后续轮次的 `level` 不得被推断上调。

## 四、改造方案（分层，按性价比排序）

### P0 提示词层（零数据改动，当天可落地）

- `game_router.build_common_rules()` 重写「剧透管理」：
  - 把「剧情推进型游戏」的判定改为**按游戏标注**，不再靠举例：在
    `game_registry.py` 每个游戏加一个 `spoiler_axis` 字段
    （`act` / `chapter` / `ability` / `none`），BG3 = `act`，
    CP2077、VA-11 Hall-A = `chapter`，空洞骑士、丝之歌、泰拉瑞亚 = `ability`，
    缺氧、MHW = `none`。
  - 规则明确：**用户报过进度后，进度构成硬上界**，后续回答不得越过；
    再次提问时不再重复追问进度；用户若说「别剧透后面」，必须在作答前复述边界
    （「你现在在最后之光旅店，我只讲这一带」）。
  - 明确「超出上界」不得正向描述（不给名字、不给结果），只允许
    「还有后续，等你到那儿再说」这类占位提示。
- `game_registry.py` BG3 `extra_prompt` 补一段：说明本作三幕结构、
  常见进度锚点（第一章地表/幽暗地域 → 第二章最后之光旅店/月出之塔 → 第三章下城区），
  并说明结构化数据里 locations / quests 带 act 列可供判断。

### P1 数据层（给检索装边界，需重建 BG3 向量库）

- 结构化侧已具备条件（无需新采集）：
  `games/baldurs_gate3/data/baldurs_gate3_data.db` 的
  `locations`（249 行）、`quests`（152 行）都有 `act` 列（取值 1/2/3）。
- 建库时（`scripts/tool/mac_build.py::collect_documents()`）给文档补
  `act` 元数据：
  - 结构化 locations / quests：直接取 `act` 列；
  - wiki 文档：正文/分类里带 `Act_One_*` / `Act_Two_*` / `Act_Three_*`
    的按分类解析（BG3 wiki 的 categories 字段已经落在文本中，
    实测可用）；解析不出的**不写该字段**（视为 unrestricted）。
- `tools.search_knowledge_base()` 增加可选参数 `max_act`：
  带 filter 过滤，**缺 `act` 字段的文档默认保留**（否则纯设定类词条会被误杀）。
  注意 FAISS 的 dict filter 只做等值，区间判断要用 callable filter，或
  预先把 act 拆成 `acts: ["1","2","3"]` 列表做成员匹配（推荐后者，性能与可读性都更好）。
- 谁来决定 `max_act`：短期由模型在调用时传（提示词要求「已知进度时必须带」），
  中期由服务端 session 注入（见 P2）。

### P2 会话层（中期，需服务端参与）

- 服务端持久化 `progress`（game → act/chapter/ability），随每轮注入，
  取代从 `history` 反推；顺带解决「刷新即失忆」。

### P3 观测层（服务器侧负责）——已完成 2026-11-12

- `turn_record()` 增加 `answer_head`（答案前 200 字）与 `spoiler_hits`
  （命中后期内容 + 所属 act），命中词表在 `api_server.SPOILER_TERMS`。
- `log_turn()` 改为双写：`api_server.log`（现场）+ `data/turns/YYYY-MM-DD.jsonl`
  （追加写、重启不丢，已 gitignore）。此前日志被 nohup `>` 覆盖，重启即清零，
  多日数据无从回溯。
- 分析工具：`scripts/analysis/turns_report.py`（`--days` / `--game` / `--spoilers`），
  可出每日轮次、独立 IP、耗时 P90、游戏与路由分布、token/工具调用统计、剧透命中样本。
- 已复现的回归样本（11-12 新增，stored in data/turns）：
  问「博德之门3，我卡在最后之光旅店，附近的塞伦捏秘密任务怎么做？」时，
  回答把整条任务链从头讲到尾（废墟战场 → 陶匠的房子 → 旅店地下室 → 后续），
  `spoiler_hits` 捕获到 `Mason's Guild(act2)`。可作为 P0/P1 落地后的第一条断言用例。

#### P3 顺带发现的两个问题（待定）

1. **信号词缺口**：同一句话不加游戏名时（「我卡在最后之光旅店…」）
   路由到菜单（`route=menu`）——因为 `最后之光旅店`、`塞伦捏` 不在 BG3 的
   `signals` 里（现有的是月出之塔、下城区、利文顿、幽暗地域等）。
   有 history 的真实会话不受影响，但刷新后新会话必踩。待 Mac 侧补信号词。
2. **菜单/回退轮也扣额度**：`route=menu` 的 0.0s 响应也消耗了一次额度。
   建议只对 `route=agent` 的轮次计费（额度与成本挂钩），待拍板。

## 五、验收标准

1. 以「我卡在最后之光旅店」为前提提问旅店附近任务，回答中不出现石匠工会、
   大陵墓、月出之塔等后续区域名（黑名单比对，P3 提供自动化）。
2. 进度未知时**不追问**，按提问所指作答（方案 C，见 3.4）；报过进度后不再重复追问；
   用户明说「别剧透」时，回答开头必须出现边界复述。
4. 检索日志中 `max_act` 实际生效：Act 2 进度下不应返回 `act=3` 的 quest/location 文档。
5. 通过重建后的 `mac_prepare_build.sh` 第 5 步自检（走真实
   `tools.search_knowledge_base` 路径）+ `tests/test_mac_build_contract.py`。

## 六、待裁决

1. act 粒度够不够：地点/任务是地理维度，但「影心身世」「皇帝身份」这类是剧情揭秘维度，
   不是 act 能挡的。是否再加一个 `spoiler: core/none` 标签？建议**先不加**，
   先用提示词层兜，避免一次上两个过滤轴。
2. wiki 条目 act 推断不出来的（设定、法术、物品类）默认放行是否可接受？
   建议放行——它们通常不含区域剧情。
3. 越界时的处理风格：占位提示（「等你到那儿再说」）还是直接拒答？建议前者。

（2026-11-15 已定：未知进度走方案 C 不问；轴只做剧情三类；进度下拉归前端、
未设置就不发字段。剩下待裁决的只有下面这条。）

4. 中途降级怎么处理：「我重开了一周目」需要在同一会话里把 level 降回去，
   目前设计是只认字面声明（不靠推断），要不要支持一键「重置进度」还要看前端。
