## I-25 流式等待期全程静默，移动网络下断连 → 前端报「网络错误」【P1】

**现象**（2026-11-25 11:56:40，IP 223.104.79.66，iPhone）：

- 11:56:15 `OPTIONS /api/ask/stream` 200，随即进入 agent 工具循环；
- 11:56:15 → 11:56:37 连续 7 次 `POST api.deepseek.com` 全部 200 OK；
- 11:56:40 `WARNING 客户端断开连接`，同一毫秒 access log 记录 `POST /api/ask/stream 200 0`
  ——整个响应体 0 字节；
- 前端 `catch` 分支渲染「网络错误，无法连接到助手服务器」。

**根因**（三层，分开修）：

1. 传输层：SSE 在首 token 前不发任何字节，实测静默可达 65s（elapsed max），中间设备/浏览器把长静默连接判死。
2. 协议层：`multi_agent.ask_stream` 只在 `AIMessageChunk.content` 非空时 yield token；
   工具调用阶段 content 为空（只有 `tool_call_chunks`），所以工具循环全程无事件。
3. 前端：loading 文案静态「思考中…」，断流时 `catch` 覆盖已有内容且无重试入口。

**附带发现（服务器侧待修）**：

- 断连分支 `except (ConnectionResetError, ConnectionAbortedError)` 没有 `quota.refund()`，
  而超时分支有 → 网络原因没拿到答案也扣 1 次额度。
- 断连轮次 `route` 落库为 null、`tokens_in=0`，统计上与正常轮并存无法区分。
- `turns` 无 `first_token_ms`，「静默期」只能靠 elapsed 间接推断。

**方案**：[`STREAM_UX_PLAN.md`](STREAM_UX_PLAN.md)（L0 心跳 / L1 计时文案 / L2 真工具事件 / L3 断流恢复 / L4 断流记账）。

**验收**：`stream_chunks=0` 轮次归零、`first_token_ms` p90 有数、iPhone 移动网络下工具多轮问题不再弹网络错误。

## I-27 建库分页器不认 refetch 的 `---` 页面分隔，页面被切碎或整库塌成一页【P0，实测】

`refetch_wiki.py` 的输出里，页面之间用一行 `---` 分隔，**行数恰好等于文件头写的「总页数」**：

| 文件 | 总页数 | `^---$` 行数 | `^## ` 标题行数 |
|---|---|---|---|
| `games/terraria/data/wiki_data_zh.md` | 3031 | 3031 | 16777 |
| `games/silksong/data/wiki_data.md` | 79 | 79 | 193 |
| `games/mhw/data/wiki_data.md` | — | 有 | 18（正文用 `# 页面名`） |

而两个建库入口的分页逻辑都**没有用这个分隔**：
`mac_build.load_wiki_documents` 按 `# 文档：` / `## ` / `# ` 三种正则切，
`ingest_game.py` 同理。页内小节也叫 `##`，于是每个小节都被当成一个独立页面。

**后果分三档，越往后越严重：**

1. **terraria（切碎）**：31,248 块 / 7,347 个 title / 3,031 个页面。
   「制作」4322 块、「历史」4255、「花絮」1979、「备注」1814、「小贴士」1388，
   通用小节名合计占 **50.8%**。
   单页实测：`## 克苏鲁之眼` 原文 **5,263 字、12 个页内小节**，建库后只产出
   **1 个 344 字的块**（其余被切成 `召唤和生成`/`行为`/`后果`/`备注`/… 12 个碎片，
   title 丢失页面归属）。
2. **silksong（切碎 + 覆盖不足）**：339 块 / 129 个 title / 79 个页面。
3. **mhw（整库塌成一页）**：1,863 块，**title 只有 1 个值 `MHWilds`**。
   第一块内容是 `Redirect to: Monster Hunter Wilds ---`（文件头）。
   即整个文件被当成一页塞进 splitter，1,114KB 正文全被切成块且共用一个 title，
   引用来源永远是「MHWilds」，无法区分。

**检索实测（真实路径，`k=4`）**：

| 查询 | top-4 title | 结论 |
|---|---|---|
| terraria「克苏鲁之眼怎么召唤」 | Demon's Eye / Eye of the Golem / Face Monster / Lunatic Cultist | MISS，页面本身没进 |
| terraria「天界塔怎么打」 | Celestial Pillars | PASS |
| silksong「Silk Soar ability」 | Grand Mother Silk / Lore / Usage | MISS（库里也确实没有 Silk Soar） |
| mhw「大剑怎么玩」 | MHWilds ×4 | 判定无意义（title 全同） |

**不是 embedding 的问题**：拿「克苏鲁之眼」页块正文反查，能把自己召回（距离 4.045 排第一）。
问题在分块与 title 归属。

**修法**（Mac 侧，`scripts/tool/mac_build.py` + `scripts/tool/ingest_game.py`，两个入口都要改）：

1. 分页前先按 `(?m)^---\s*$` 切页；
2. 页内再按 `##` 切小节，**小节块的 title 必须继承页面名**，小节名另存 `section`；
3. mhw 这类 `# 页面名` + `---` 的格式走同一条路（先按 `---` 切，再按 `#` 取页名）。

**契约测试**：`tests/test_wiki_page_split.py`（2 例）。记录时是 **xfail**（问题存在的证明）；
Mac 侧 e19b994（12:36）把两条建库入口都改成「先按 `---` 切页、页内再按小节切」后，
已转为 **2 passed**（服务器侧实跑确认，xfail 标记已删）。
**注意：分页修好 ≠ 库变好**，三个库都还是旧分块，必须重建。

**验收口径**：terraria 重建后块数应接近「页数 × 2–6」而不是 ×10；抽 20 页比对
「title 与正文是否对题」；`retrieval_smoke.py --game terraria` 全 PASS。

## I-31 `fetch_k` 是「过滤前」候选数，小语种块结构性不可达【P1，实测】

I-28 修完合并顺序后，「螳螂爪怎么获得」仍 MISS，但与「块不在库里」无关：
`games/hollow_knight/vectorstore` 里 `Mantis Claw`（en，620 字）与 `螳螂爪`（zh，250 字）
两个块都在。实测把 `fetch_k` 换成全库大小重排：

```
螳螂爪块全局排名：532 / 1960     距离 9.1601
全局 top-5：Longnail 7.676 / The Collector 7.792 / Collector 7.844 / Nailsmith 7.865 / Sly 7.886
zh 块最佳排名：150，最差：1934（zh 共 47 块 / 1960）
```

根因是 langchain `FAISS.similarity_search_with_score` 的语义：它先按 `fetch_k` 取**全局**
最近邻，再叠加 `filter` 过滤，凑够 `k` 就停。`fetch_k=200` 时 47 个 zh 块里只有排名
≤200 的才可见，螳螂爪排 532 → 永远取不到，且「zh 路只返回 1 条」看起来像库空，
容易误判成建库问题。BG3（66,698 块、全 en）不受影响，HK/ONI/VA11 这类中英混合库必中。

修法候选（属主检索链路，需用户拍板后再动）：
1. 按库大小动态抬高 `fetch_k`（HK 1960 → 全库；BG3 66k 则不宜），风险是 BG3 变慢；
2. 按语言建独立 FAISS 索引（彻底，但要改建库产物与加载层）；
3. 先拿语言分布估算 `fetch_k`：`fetch_k ≈ k * total / lang_blocks`，用元数据算不额外查询。

附带发现：zh 块本身质量也差（250 字里夹「本站由于网络原因 已迁移至…欢迎编辑加群」
导航垃圾），距离 9.16 与 top-1 7.68 差距大，单靠调 `fetch_k` 只能把排名 532 的块拉进
候选池，是否真的进 top-k 还要实测。数据面正解是 I-28 说的补 HK 中文 wiki。

## I-25 复现记录（12:37 那轮 iPhone）+ 首字节与心跳修复

### 现场

```
12:37:21  POST /api/ask/stream  UA: iPhone OS 18_7, Safari (163.125.180.89)
12:37:22  DeepSeek #1 200
12:37:25  📥 加载向量库 oni（冷启动）→ 2120 向量
12:37:25~35  DeepSeek #2..#6（5 次工具循环，每轮 2~4s）
12:37:44  WARNING 客户端断开连接: 163.125.180.89  | 22.5s | 0t
```

落库的 turn 记录是 `route=None / elapsed=None / stream_chunks=0 / tool_calls=0`——
客户端断开时生成器被取消，`log_turn` 那一步没执行到。

### 结论

不是服务端报错，是 **22.5 秒里一个字节都没写到响应体**：

1. `ask_stream` 的第一次 LLM 调用就要 4~9s；
2. 这轮又撞上 oni 向量库冷加载（+3s）和 5 次工具循环；
3. 期间只有 `progress` 事件，间隔本身也可能十几秒。

iPhone Safari 对「长时间没有响应体字节」很敏感，判定连接异常后断开，前端
`reader.read()` 抛错，`catch` 一律显示「网络错误」。

### 修复（服务器侧，api_server.py）

1. **首字节立刻落地**：`resp.prepare()` 之后马上写 `: open\n\n`，TTFB 从秒级压到毫秒级。
2. **心跳**：`ask_stream` 的产出改为经 `asyncio.Queue`，主循环用
   `asyncio.wait_for(queue.get(), timeout=keepalive_s)` 取事件；超时就写一行
   `: keepalive`（`keepalive_s` 默认 8s，可通过 api_config.json 调）。
   SSE 注释行不是 `data:` 开头，前端解析器直接忽略，不影响事件流。
3. 上游生成器改为独立 task（`_pump`），客户端断开时 `finally` 里取消，
   LLM 调用不会在后台空转烧 token。
4. 上游异常不吞掉，用哨兵值 `("__raise__", e)` 还原成普通异常抛到原 except，
   保持「断流时不写 done」的既有契约（否则前端状态机会错乱）。
