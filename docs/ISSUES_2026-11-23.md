# ISSUES 2026-11-23

## I-24 路线类问题讲不清楚（数据层从来没通）

**现象**（用户 2026-11-23 反馈）：线上问「怎么去 / 路线 / 往哪走 / 入口在哪」这类问题，
回答讲得让人走不起来。典型样本（`data/sessions.db` 与 `data/turns/*.jsonl`）：

- 「给我整个 xy 点位路线」「码头传送点往哪走」——答案主体是一串 `X:-219 Y:-155`，
  外加「Y 值几乎一样，意思是沿着水岸一路往东走就行」。**方向是从坐标数字推出来的**，
  wiki 原文没有这句；坐标本身可用（见下），推出来的方位不可用。
- 「bg3 怎么去铁王座」——步骤对（潜艇、Flymm Cargo、炸厂后不可逆都在），但只给
  「西侧双门 X:-169 Y:-149」这类端点，**没有起点**：玩家不知道从哪个传送点起走、路上先碰什么。
- 「下水道里在哪找到明斯克」——「最西端」同样是从文本碎片拼的方位。

口径纠正（2026-11-23 用户指出）：BG3 右上角小地图**实时显示 X/Y**，坐标是玩家能对照的
导航语言，不能砍也不能弱化。缺的不是坐标，是「起点 + 约束链 + 可跟随的分解」。

### 取证

BG3 结构化库 `games/baldurs_gate3/data/baldurs_gate3_data.db`：

| 项 | 现状 |
| --- | --- |
| `locations` 行数 | 249（`act` 填充 174） |
| `connected_locations` | 73 条有值，**73/73 都把整页正文塞进 JSON**；源头是 wiki 页顶的 `↑ / ↓` 导航条，是「同分类上一个/下一个条目」，不是游戏内连通 |
| `waypoint` | **0/249**，抓取正则 `Waypoints?\s+\[edit section` 从未命中（wiki 里的形式是 `Waypoints [ edit section \| visual editor ]`） |
| 坐标字段 | 不存在。坐标只散落在 `description` 与 wiki 正文里 |

`scripts/build/build_bg3_db.py:parse_location()` 是这两列的产出点。

关键反差：**wiki 正文其实什么都有**。以 `Lower City Sewers` 页为例，正文里有入口表
（Entrance / General Area / Location / Sewers Location / Outside Access）、门的坐标与
DC（`DC 15 Sleight of Hand`）、连通句（`Following the large pipe in this room leads to
the Abandoned Cistern`、`connects to almost every other location of the Undercity`）、
Waypoints 小节（`City Sewers at X: -98 Y: 779`）。Grey Harbour Docks 页同样有
`This location contains the following Waypoint: Grey Harbour Docks at X: -219 Y: -155`。

所以不是没数据，是**结构化层没通 + 回答格式没约束**。

### 根因

1. **数据层**：`connected_locations` 是脏字段（导航残留 + 正文污染），`waypoint` 全空，
   没有坐标列。工具查 `locations` 拿不到任何路线信息，等于路线问题走不了结构化通道。
2. **工具层**：`query_structured_data` 按「数值列 / 名称」匹配，不认路线意图，
   `locations` 的邻接、`waypoint`、入口表都不会被主动查。
3. **提示词层**：没有「路线怎么答」的约束，模型把坐标当向量做算术推方位
   （`Y 值几乎一样 → 往东走`）。坐标可见不代表方位可推——X/Y 与地图朝向的对应关系
   在 wiki 里没有依据，推出来的方向可能正好相反。同时缺起点：不先说「最近传送点是
   哪个、坐标多少」，只给目标坐标等于把最后一段留给玩家自己摸。

### 建议（按顺序）

**A. 数据层（Mac 侧，scripts/build/build_bg3_db.py）**

- `waypoint`：改正则抓 `This location contains the following Waypoints?: <名> at X: … Y: …`，
  拆成 `waypoint_name` + `waypoint_x` + `waypoint_y`。按抽样估能补上几十条。
- `connected_locations`：**先停用而不是修**。现在的值对模型只有害处；
  改成从正文 `leads to / connects to / following … leads` 句子抽有向边，
  每条带 `evidence`（原句），没有原句的边不写。
- 入口表：`Lower City Sewers` 这类页面的 `Entrances` 表是导航金矿，
  抽成 `location_entrances(from, to, gate/dc, evidence)`。
- 坐标抽取：112/249 个地点名在正文里带坐标，其中 82 个是多点位（同一地点被提到多处
  不同坐标），要区分「区域坐标」与「具体点位坐标」。有了它，工具可以按欧氏距离算
  「距目标最近的传送点」——确定性几何，不靠模型推方位。
- waypoint 全量：`contains the following Waypoints` 小节点名的只有 9 个（实际游戏 40+），
  要从正文里所有 `xxx Waypoint at X: … Y: …` 补齐，否则「最近传送点」算不出来。

**B. 工具层（Mac 侧，src/rag_agent）**

- 加路线意图（`怎么去 / 路线 / 往哪走 / 入口 / 传送点`）→ 走 `locations` 专查，
  返回 act + waypoint + 入口 + 带 evidence 的相邻边，而不是现在的通用数值查询。

**C. 提示词层（Mac 侧）**

- 路线回答格式固定：① **起点**（最近传送点名 + 坐标）② 地标链 + 门/DC ③ 不可逆限制。
- 坐标照给（小地图可对照），但禁止用坐标数值推断方位；只有 wiki 原文写了
  `north/west/east of` 才说方位。

**D. 评测（服务器侧）**

- 加 5–8 条路线 golden case（铁王座、废弃蓄水池找明斯克、希望之邸入口、下水道三入口），
  判据四条：命中正确起点传送点；命中目标入口/地标；不出现无原文依据的方向推断；
  act 不越界。
