## 1. 数据说话

`data/turns/*.jsonl` 全量 141 轮（11-12 到 11-17）：

| 指标 | 值 |
|---|---|
| tokens_in 合计 | 10,030,871 |
| tokens_in p50 / p90 / p99 / max | 48,294 / 152,903 / 282,434 / 552,010 |
| tokens_out 合计 | 303,002 |
| history_msgs p50 / p90 / max | 37 / 149 / 179 |
| 单轮平均 tokens_in / history_msgs | 1,238 token / 条 |

11-16 一天 63 轮的内部对比更清楚：

| 时段 | 平均 tokens_in |
|---|---|
| 当天前 10 轮 | 58,145 |
| 当天后 10 轮 | 179,547 |

tokens_in 与 history_msgs 的相关系数 0.668。也就是说，增长主要不是问题变复杂，而是历史越堆越长。晚上 23:11 那轮「不是 AC 都是 12，一个是条件隐蔽+3 一个是常驻隐蔽+1」只有 26 个字，输入却有 46,949 token，其中绝大部分是前面 170 条历史。

耗时跟着涨：当天前 10 轮平均 6 秒级，后 10 轮 20 到 35 秒。按 141 轮、10M token_in 计算成本，一个月的高强度使用会把额度模型打穿。

## 2. 根因不在模型侧

前端每一轮都把整个会话重新序列化发上来：

```js
// htmls/hollow_knight.html
for (let i = 1; i < this.messages.length - 1; i++) { ... history.push(...) }
```

服务端把 `history` 原样交给 `build_messages`，没有任何长度控制。所以本质上「上下文窗口」是由用户聊多久决定的，不是我们决定的。

这也是为什么刷新页面就失忆、换设备就断档，同时单次请求又大得离谱，两头都不对。

---

## 3. 方案 A：服务端裁剪（本周可做，改动小）

### 3.1 位置

在 `handle_ask` / `handle_ask_stream` 里，**先反推游戏，再裁剪**。

顺序不能反。`_game_from_history` 需要看完整历史才能找到游戏锚点，裁完再看可能就把锚点裁掉了。正确顺序：

```
history_raw = body["history"]
hist_game   = _game_from_history(history_raw)      # 用完整历史
history     = trim_history(history_raw)            # 再裁
ask(question, history=history, ...)
```

### 3.2 裁剪规则（纯函数，可单测）

`trim_history(history, max_turns=6, max_chars=6000, keep_head=1)`：

1. 保留首轮 user 消息（通常是定游戏、定流派的那句，是整段对话的锚点）。
2. 从最新往回取，最多 `max_turns` 轮（一问一答算一轮），累计字符超过 `max_chars` 停止。
3. 永远保留最后一条 user 消息（就是本轮问题之前的那条），即使已经超预算。
4. 单条消息超过 2000 字时截断到 2000 字，尾部加「（后略）」。长表格式回答最容易爆。
5. 裁剪后如果第一条不是 user，丢到第一个 user 为止（避免开场是孤立的 assistant 消息）。

预期效果：6 轮按平均 1,238 token/条估算约 1.5 万 token，加 system prompt 和检索结果，单轮输入控制在 20 到 30k，p90 从 152,903 降到 40,000 以内。

### 3.3 观测

turn 记录增加三个字段，不动现有字段：

- `history_raw_msgs`：前端发来的条数（现有 `history_msgs` 保持原义，改成裁剪后条数会破坏历史数据可比性，所以新增）
- `history_used_msgs`：实际送进模型的消息数
- `history_trim_chars`：裁掉的字符数

这样每天能直接看到裁剪生效情况，也能反推还有多少历史是必要的。

### 3.4 风险与缓解

| 风险 | 缓解 |
|---|---|
| 裁掉前面说过的流派设定，模型答偏 | 保留首轮 user；6 轮窗口对「持续追问同一套装备」的场景够用（实测这类追问间隔不超过 3 轮） |
| 裁剪把游戏锚点裁掉 | 先反推游戏再裁，且 `last_game` 已由 `hist_game` 参与路由 |
| 单条超长回答撑爆预算 | 单条 2000 字截断 |
| 用户聊到 30 轮后发现模型「忘事」 | 这是可接受的取舍，比每轮 55 万 token 便宜得多；中期用 session 存储 + 摘要解决 |

## 4. 方案 B：会话收归服务端（中期）

方案 A 治的是单轮成本，不解决「刷新即失忆」。中期按已有设计做：

- `store.py` 建 `sessions` / `turns` 表（SQLite WAL、busy_timeout、每请求连接），前端只发 `session_id` + 本轮问题。
- 裁剪从「客户端历史」变成「服务端查询最近 N 轮」，顺带解决多设备连续对话。
- 与评测样本池共用同一张表：`feedback` 表按 turn_id 关联，人工点赞/点踩的样本可直接导出成 golden set。

迁移路径：

1. 方案 A 先上，前端不用改，历史仍由前端发送（但服务端会裁）。
2. 引入 `session_id`，前端同时发送历史与 id，服务端以历史为准但记录 id。
3. 切到服务端权威，前端停止发送历史，只发 id 与问题。

任何一步都可以单独回滚，不影响另一步。

## 5. 验收标准

实现完成后必须由服务器侧实跑：

1. `tests/test_history_trim.py`：6 条纯函数用例（首轮保留、末轮保留、字符上限、单条截断、轮数上限、孤立 assistant 丢弃）。
2. 回放 141 轮真实历史，统计裁剪前后 tokens_in 分布。目标：p50 ≤ 25,000，p90 ≤ 40,000，max ≤ 80,000。
3. 抽 10 条跨 10 轮以上的真实会话做端到端问答，确认「前面定过的流派、选过的装备」仍能被正确引用，答案不退化。
4. 观察一天线上数据，`history_used_msgs` 与 `tokens_in` 的相关系数应显著低于现在的 0.668。
