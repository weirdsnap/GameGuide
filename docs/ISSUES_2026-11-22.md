## I-09 长会话上下文仍无裁剪（P0）

现象：11-22 00:27「如何增加卡拉克的体质」单轮 tokens_in 290,355、耗时 44 秒、history 87 条。
11-22 当天 11 轮里 p50 就已是 103k。

证据：

```
tok_in>10 万 的轮次 46 / 203（全量），全部出现在长会话尾部
11-22 00:21  hist 79  tok 150,306   塞夫洛被杀了送到营地了？这是什么情况
11-22 00:22  hist 83  tok 119,606   不是，塞夫洛的尸体被奥林拿来送信给我们
11-22 00:27  hist 85  tok 290,355   如何增加卡拉克的体质
```

根因：前端每轮重发完整历史，服务端 `handle_ask*` 不裁剪。方案与验收线已在
`docs/CONTEXT_BUDGET_PLAN.md` §3.2（`trim_history`），**至今未实现**，所以数据仍在原地。

本轮新增结论：`tokens_in` 与 `elapsed` 同步线性上涨（p90 耗时 21.6s → 38.6s），延迟问题
不是模型变慢，是输入变长。裁剪落地后两件事一起解决。

验收线（在 CONTEXT_BUDGET_PLAN 原值上补充）：

- p90 tokens_in < 40,000，单轮 max < 80,000
- 长会话第 20 轮以后 p90 耗时 < 15s
- 裁剪不能切断游戏锚点：裁剪后 `_game_from_history` 仍能反推对游戏（否则短追问落菜单）

## I-10 检索条目不带 act，模型把第三章的事实改写成第二章（P0，两轮点踩已证实）

现象（`data/feedback/2026-11-22.jsonl`）：

| 时间 | turn_id | 问题 | 轮次表现 | 反馈 |
|---|---|---|---|---|
| 01:06 | `9aa9420690ae` | BG3 山丘巨人的铁手套是什么 | hist 1 / tool 3 / 8.5s | 👎 |
| 01:07 | `398fb6fc3fd9` | 赫尔希克需要我们给她这个手套 | hist 3 / tool 6 / 22.0s | 👎 |

第一轮答物品数值（正确），但把位置说成「第二章」；第二轮自我纠正：「我之前说在第二章，
这点我纠正一下，唯一一副在拉斐尔的希望之邸（House of Hope）」。用户两轮都点踩。

**根因不是数据缺失，也不是幻觉。**数据库里这条记录完整且带 act：

```
armor.Gauntlets of Hill Giant Strength
  where_to_find = "House of Hope X:-6549 Y:2940 : on a pedestal in the Archive ..."
locations.house_of_hope.act = 3
quests.acquire_the_gauntlets_for_helsik.act = "3"
```

问题出在传递链：

1. `query_structured_data` 把 `where_to_find` 原样拼进文本返回，**不带 act**。模型手上只有一串
   英文地名，没有「这是第三章」的信息。
2. 提示词没有「不得把条目所属章节改写成用户当前章节」的规则。模型默认「你在第二章」
   等于「答案也在第二章」，于是把 act 3 的藏品对到了 act 2。
3. 审计词表 `SPOILER_TERMS` 没有希望之邸、拉玛吉斯之塔、法术杂货铺这些 act 3 地名，
   所以这轮 `spoiler_hits` 是空的，事后统计抓不到这次泄露。

方案（三层，互不依赖，可从任一层先做）：

**A. 工具层（Mac）**：条目返回时附 act。armor/items 用 `where_to_find` 里的地名 join
`locations.act` 得到 act（join 不上就不写，别猜）；quests/locations 直接取 `act` 列。
最小实现：条目文本尾部加 `[act 3]`，不改返回结构。

**B. 提示词层（Mac）**：`build_common_rules()` 补四条：

1. 检索条目的章节以条目自身为准，不得改写为用户当前进度所在的章节。
2. 条目 act 高于用户进度时，只给「存在 + 获取前置条件」，不写具体地点、不给任务链。
3. 字段缺失（如无 `where_to_find`）时一次说清「库里没有位置信息」，不留「可能在某处」这种半句。
4. 进度未知时（`progress_prompt_note` 返回空串的情况）不得替用户假设章节，条目属哪章就按哪章说，
   不确定就不写章节——这一条与 I-14 是同一个改动点。

**C. 审计层（服务器）**：`SPOILER_TERMS["baldurs_gate3"]` 补 act 3 地名（L1）：
`House of Hope / 希望之邸 / Ramazith's Tower / 拉玛吉斯之塔 / Sorcerous Sundries / 法术杂货铺`。
顺带给 `turn_record` 加 `entry_acts`（工具返回条目里出现的 act 集合，去重、上限 10），
供离线统计「返回了 act3 但用户进度是 act2」的比例。

## I-14 模型默认「你在第二章」（P0，用户主观感受，数据能对上）

现象：用户口述「模型总是默认我在第二章」。铁手套那轮 `hist_msgs=1`，是纯新会话，问题里
没有任何章节信息，答案直接编出「第二章」。

两个成因叠加，都被同一次测序证实：

1. **进度未知时提示词零约束**。`infer_progress` 推断不出就返回 `level=None`，
   `progress_prompt_note` 对这种情形**返回空串**（注释写的「走方案 C，不追问」）。
   模型手里没有任何进度声明，只能按世界知识往中期（第二章附近，游戏时长最长的部分）猜。
2. **进度单调取 max + 历史全量**。一旦历史里出现过「第二章」「月出之塔」这类锚点，
   `progress.level` 就永久钉在 2（除非新问题里出现了更高的锚点）。配合 `ACT_LIMIT`
   在检索层过滤 act3 文档，模型手里只剩 act2 的内容，于是出现 I-10 那种「act3 事实被安放到
   第二章」的改写。

为什么不能直接改第 2 条：单调不减是防剧透的地基（多来源取 max、提问即授权），改它等于
把「用户明明到了第三章却被按在第二章」换成反方向的漏洞。

建议（按成本排）：

1. **提示词一句（成本最低，建议先做）**：`progress_prompt_note` 在 `level=None` 时不要返回空串，
   而是注入：「用户没有说过进度：不要替用户假设章节；条目属于哪一章就按哪一章说，
   不确定就不写章节。」
2. **观测（服务器）**：`turn_record` 加 `progress_level` 与 `progress_source` 两个字段
   （现在没落），才能离线量出「进度=2 的轮次占比」「未知进度占比」，也给不了改进前后的对比。
3. **不建议**：给进度加「超时降级」或「用户否认就清空」——进度对象是硬上界，静默松动会让
   剧透重新漏回来。真要变，走 SPOILER_CONTROL_PLAN 的多来源取 max，不另立规则。

### I-16 缺陷 B 未修，现在正在产生假阳性（P1，阻塞内容层读数）

`bg3-lorrokan-act2` full 实跑报告：

```
伪造来源（工具返回里找不到）：['博德之门本地法师', '洛若坎']
剧透超过 L1：[('Nightsong', 'act2', 'L3')]
```

第一行就是 EVAL_SYSTEM 里记的缺陷 B：`check_citation()` 把正文引号当来源，人名「洛若坎」被
当成伪造引用。真越界（Nightsong）和假阳性混在同一条里，读报告的人分不清。
**缺陷 A 修完反而把 B 的噪音暴露得更明显**。建议 A、B 一起修，只修 A 等于换一种噪音。

### I-17 提示词三条规则在打架（P1）

同一份 `build_common_rules()` 里同时存在：

1. `game_router`：「用户问题涉及剧情且尚未报进度时，先追问玩到第几章」
2. `progress.progress_prompt_note`（本次新增）：「不要替用户假设章节」
3. `SPOILER_CONTROL_PLAN`：「未知进度不追问」

三句话同时进 prompt，模型听哪句看运气。已定的口径是不追问（追问会反复打断用户），
所以应删掉第 1 句，改成「按条目自身 `[act N]` 作答，用户报过进度才套上界」。

### I-18 `_row_act` 两处脆弱点（P2）

1. **多地名时取 dict 遍历顺序的第一个**。实现是 `for name, act in act_by_title(...).items(): if name in where: return act`，
   条目 `where_to_find` 一旦同时提到 act2 与 act3 的地名，标哪个全凭表里的插入顺序。
   防剧透场景建议取 `max(act)`：宁可多屏蔽，不要漏。
2. **act 标注只覆盖关键词全表搜索**。走 `_format_db_result` 的数值筛选（「所有轻甲」「列出所有武器」）
   返回行里没有 `[act N]`，模型照样会自己安章节。这类请求在 11-16 的单轮 19 次工具调用里占大头。

### I-19 `trim_history` 的 `max_turns=6` 对短消息会话偏激进（P2）

预算判断是「条数 ≤ 2×(`keep_head`+`max_turns`) 且字符 ≤ 6000 才不裁」，所以 60 条各 10 字的
短历史（总共 600 字）也会被裁到 7 轮。线上 `history_msgs` p50 = 31，等于大部分会话都被砍到
最近 6 轮 + 首轮。对同一条任务聊十几轮的 RPG 场景可能太狠（在任务中途会忘掉前面的线索）。
建议 `max_turns` 放 10–12，或字符远低于预算时不按轮数裁。裁完头 3 天看 tokens_in 与点踩率再定。

## I-21 gauntlets 用例的字面禁词与正确性自相矛盾（2026-11-22 服务器侧复核）

`bg3-hill-giant-gauntlets` 的 `forbidden_terms` 含「第三章」「希望之邸」「拉玛吉斯」「法术杂货铺」，

[KNOWN] bg3-hill-giant-gauntlets

判断依据是答案里的「第三章」是否为回答「在哪拿」所必需 —— 是必需，就不该禁。

## I-22 pytest 请求写脏生产 turns 数据（2026-11-22 服务器侧数据分析发现）
